Продолжаем разработку Solana Launchpad. Этап 1 прошёл GitHub Actions. Начинаем этап 2: совместимое создание кампании V2.

**Работай только над созданием V2-кампании. Не подключай новые параметры к внесению SOL, возвратам, API или интерфейсу.**

### 1. Сначала проверь текущую реализацию

Перед изменениями изучи:
- существующий `Campaign` и его `SPACE`;
- инструкцию `start_campaign`;
- PDA seeds и способ формирования `campaign_id`;
- существующие Anchor account constraints и ошибки;
- текущие Rust unit-тесты и ProgramTest;
- точную реализацию `CampaignParameters`, `ValidatedCampaignParameters` и `validate_campaign_parameters`, добавленных на этапе 1.

Не предполагай, что детали совпадают с предыдущим аудитом: ориентируйся на текущий код.

### 2. Добавь отдельный аккаунт V2

Создай новую структуру `CampaignV2`, не изменяя старую `Campaign`.

В V2 должны сохраняться как минимум:
- создатель кампании;
- идентификатор кампании;
- время создания;
- конечный дедлайн;
- количество участников;
- текущее число участников;
- общий объём внесённых lamports;
- статус кампании;
- сумма взноса в USD cents;
- целевое число участников;
- длительность в минутах.

Используй типы, совместимые с Anchor/Borsh. Рассчитай точный `CampaignV2::SPACE`, включая дискриминатор Anchor, и добавь тест на достаточность выделенного размера.

Для конечной кампании вычисляй дедлайн через checked arithmetic. При переполнении возвращай ошибку. Не создавай кампанию с недопустимыми настройками.

### 3. Добавь `start_campaign_v2`

- Принимай параметры кампании как аргументы инструкции.
- Валидируй их непосредственно в on-chain программе через существующую функцию этапа 1.
- Сохраняй только проверенные параметры.
- Создавай V2-аккаунт с отдельными PDA seeds, чтобы он не конфликтовал с V1.
- Сохрани проверку полномочий создателя и защиту от повторного создания того же PDA.
- Возвращай понятные Anchor-ошибки при недопустимых параметрах и переполнении времени.
- Не используй значения по умолчанию вместо отсутствующих или неверных аргументов.

### 4. Обязательные ограничения

- Не изменяй V1-инструкции, `Campaign`, `Campaign::SPACE` и существующие V1 seeds.
- Не изменяй зависимости, lockfile, Program ID, toolchain или GitHub Actions.
- Не подключай V2 к `contribute`, `refund` или расчёту SOL-платежа.
- Не добавляй вывод средств, реальные транзакции, новые источники курса, API или UI.
- Не реализуй `NoDeadline`: текущая валидация должна продолжать отклонять этот режим.
- Не создавай коммит и не отправляй изменения в GitHub.

### 5. Тесты

Добавь тесты на:
1. успешное создание V2 с минимальными допустимыми параметрами;
2. успешное создание V2 с максимальными допустимыми параметрами;
3. сохранение всех переданных и вычисленных полей;
4. отказ при сумме ниже $10 и выше $100;
5. отказ при количестве участников ниже 2 и выше 100;
6. отказ при длительности меньше 10 и больше 60 минут;
7. отказ для `NoDeadline`;
8. отказ при повторном создании того же V2 PDA;
9. корректность размера `CampaignV2::SPACE`;
10. безопасный расчёт дедлайна и отказ при переполнении.

Используй существующую тестовую архитектуру проекта. Если для доказательства поведения инструкции нужен ProgramTest, добавь соответствующие проверки. Не ограничивайся тестированием чистой функции валидации.

### 6. Проверка и отчёт

Запусти:
- `cargo fmt --manifest-path onchain/Cargo.toml --all -- --check`;
- целевые Rust unit-тесты;
- существующий полный runner, если среда позволяет.

Если Replit блокирует полный runner из-за `io_uring`, не обходи проверку и не заявляй, что интеграционные тесты прошли. Подготовь код для последующей проверки через GitHub Actions.

В конце покажи:
- список изменённых файлов;
- полный diff;
- фактические команды и результаты проверок;
- подтверждение, что V1 не менялась;
- любые оставшиеся риски или ограничения.

После реализации остановись и дождись моей проверки. Не выполняй commit или push.
